# RC109 — P3 Push: حماية تسجيل FCM/APNs عبر تبديل الحسابات

**القاعدة المعتمدة:** `adnan118/Fable_flutter@39d9cc2ac91515d27363758f4d5973e59a3392e7` (RC108، CI نجاح 3/3).

## الفجوة
التنفيذ السابق كان يلغي Token الجهاز عند تغير الهوية **إذا** كان تسجيل سابق قد اكتمل،
لكنه لم يكن يغطي بصورة كافية طلبات إذن الإشعارات أو قراءة Token أو تحديثه وهي
ما زالت معلّقة؛ ولا يضمن ترتيب التسجيلات المتزامنة عند `onTokenRefresh`.

## التعديلات
- `FablePushDeviceRegistration` يقرأ إصدار الهوية الحالي ويراقب أحداث Auth
  منذ إنشائه، وليس بعد أول تسجيل ناجح فقط.
- كل طلب إذن، والتحقق من APNs، وجلب Token، وطلب تسجيل Backend يتحقق من
  ثبات جيل الجلسة. تغير الحساب يُبطل الطلب الجاري محليًا.
- عمليات تسجيل/إلغاء التسجيل وحذف Token محليًا تتسلسل داخل طابور واحد، بدل
  إرسال تحديث FCM قديم بعد تسجيل Token أحدث. النتيجة المتأخرة لا تُنسب إلى
  المستخدم الجديد.
- إلغاء الجلسة يوقف الاشتراك في تحديثات Token، ويحاول حذف Token الجهاز.
  إذا فشل الحذف، يمنع تسجيل حساب جديد حتى تنجح محاولة تنظيف لاحقة.
- الموافقة التي قدّمها المستخدم A لا تنتقل إلى المستخدم B تلقائيًا. إعادة التسجيل
  عند `resume` لا تطلب إذن النظام مرة ثانية، ولا تعمل حتى تحدث موافقة
  صريحة في الجلسة الحالية، وتكون APNs جاهزة على iOS.
- `PushTokenPlatform` واجهة Native اختيارية للاختبارات؛ النسخة الفعلية
  `FirebasePushTokenPlatform` تستخدم Firebase Messaging بلا تعديل عقود
  الخادم. لا يُولّد المشروع Firebase config أو credential مزيفًا.
- مسار Fable يستخدم `FableAuthGateway.session.identityRevision/identityEvents`
  مباشرة. مسار Other Backend يطالب صراحة بمصدر هوية وأحداث من **جلسته
  المستقلة**، ويُرفض بدونهما. لا تُنقل جلسة Fable إلى Backend آخر.
- Logout يستدعي `unregisterCurrent` قبل إبطال الجلسة حين يكون الاتصال متاحًا،
  ويمنع طلب DELETE قديم من استخدام جلسة حساب جديد في وقت إرسال الطلب.
  Backend يظل مسؤولًا عن إبطال ارتباط Token بالجلسة بشكل نهائي.

## محاكاة RC109
`packages/features/fable_push_notifications/test/push_token_session_race_rc109_test.dart`
يستبدل Native FCM/عمليات HTTP بمزود وهمي قابل للضبط و`Completer` لفرض
الترتيبات: A→B أثناء إذن النظام، أثناء `getToken`، وبعد `POST` متأخر،
وFCM token refresh متلاحق، و`DELETE` منتظر، وفشل حذف Token، واستعادة iOS
مع APNs غير جاهزة، ورفض مصدر Auth غير موثق للباك الآخر.

## حدود هذه الدفعة
- لا تختبر المحاكاة Firebase APNs/FCM الفعلي، صلاحيات النظام، سلوك الـBackground،
  أو تأكيد إبطال جلسة/Token من قاعدة بيانات Backend؛ هذه متطلبات P6.
- لا يستطيع Flutter إلغاء mutation وصل إلى Backend، حتى عند حذف Token محليًا؛
  يجب اختبار إبطال ارتباط الجهاز عبر Logout/Session Revocation على الخادم.
- لا يُثبت وجود FCM token حق المستخدم في عرض محتوى الإشعار، فالسيرفر وحده
  يطبق قيود الجمهور والصلاحيات.
- رسائل الصندوق Inbox والتصفح بعد الضغط تبقى محمية بإصدار الهوية من RC108.
- لا يتم رفع `liveE2EVerified` أو `complete` نتيجة هذه المحاكاة.
