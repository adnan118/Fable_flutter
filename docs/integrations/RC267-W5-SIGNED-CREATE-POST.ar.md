# RC267 — أول مسار كتابة آمن للمشروع المولّد

**الحالة:** تنفيذ مصدر مدمج للمولّد، وليس دليل اختبار Backend أو أجهزة فعلية أو تصريح إنتاج.

## ما أصبح ممكنًا

عندما يستورد المشروع عقد Backend Fable الموثّق مستقلًا، ويختار ميزة خاصة تحتوي عملية **POST لإنشاء سجل** مع طلب واستجابة JSON مسطّحين موثّقين، ينشئ `wizard:feature:generate` معها:

- Domain Repository وEntity، وData DTO خاص بالطلب والمخرجات.
- UseCase وController بحالات تحميل ونجاح وفشل.
- شاشة إنشاء تُدخل حقولًا نصية محدّدة من العقد، وتستدعي نافذة تأكيد قبل الكتابة.
- مسار `FableFeature` محمي ببصمة العقد والطريقة والمسار والصلاحيات، مع تجاهل النتيجة بعد تبدّل هوية المستخدم ومنع ضغطتين متزامنتين على التأكيد.
- اختبارات مصدرية وWidget test مولّدة؛ عبر `--wire-app` يمكن ربطها بتطبيق المشروع مع نسخ احتياطية مثل RC266.

## الحدود اللازمة للأمان

يدعم المولّد فقط عمليات `GET` السابقة، وعمليات `POST` المنتهية في `.create` والمحددة بشكل قطعي في العقد، والتي تحتوي **جميع حقول الطلب المطلوبة نصية** وتطابق توقيع عملية Backend، مع JSON object نجاح من نوع معروف. لا يُسمح بتوليد عمليات أموال أو هوية أو رموز سرية أو إدارة من هذا المسار العام.

**لا يوجد إعادة إرسال تلقائية لطلبات الكتابة:** سياسة `FableRetryPolicy` الحالية تسمح بإعادة محاولة GET/HEAD فقط. عند انقطاع الاتصال بعد POST، قد تكون العملية قد نجحت في الخادم؛ لهذا لا تُفسَّر المهلة الزمنية على أنها عدم إنشاء، وتعرض الشاشة ضرورة التحقق من حالة الخادم قبل طلب آخر.

لم أفتح PUT/PATCH/DELETE بهذا التعديل. يلزم لهذه العمليات عقد يحدد سياسة التزامن/المراجعات وعمليات التأكيد والصلاحيات لكل حالة، ولا يجوز تخمينها.

## الأدلة والالتزامات المفتوحة

- فحصت تنفيذ المولّد المنعزل لمسار POST: ثلاثة اختبارات تحقق منطقية نجحت؛ وفحصت أن مسار GET القديم ما زال يولد مصدرًا متوافقًا.
- لم أشغّل مشروع Flutter على SDK ولا اختبارات Android/iOS أو قاعدة بيانات Fable فعلية. لا يُعدّ توليد المصدر إثباتًا على توفر endpoint في مشروع معين؛ العقد الموقّع هو الشرط.
- W5 لا يزال يضم بقية عمليات الكتابة وتكامل المشاريع الحقيقية؛ W6 وW7 وW8 واختبارات الأداء/الأمان والاعتماد النهائي ما زالت مفتوحة. **Production: NO_GO.**
