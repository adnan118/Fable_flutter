# RC276 — التحقق من وضع الاستجابة في البحث والترقيم

## المشكلة

يدعم Backend RC274 البحث في **جميع** السجلات المسموحة عبر استعلام قاعدة بيانات مرقّم، وتدعم شاشة Flutter مولّد RC273 البحث وInfinite Scroll. قبل RC276 كانت Data DTO تتحقق من أن `meta.mode` أحد `page` أو `search`، لكنها لم تتحقق من أن النوع المستلم **هو نفسه** الذي طُلب في الاستعلام. لو أعاد الخادم `page` عند إرسال `q` و`mode=search` فقد يعرض التطبيق نتائج عادية على أنها نتيجة البحث، بلا رسالة خطأ.

## الإصلاح

- تمثيل `meta.mode` كقيمة Typed داخل Domain Entity: `ListMode.page` أو `ListMode.search`، بلا تمرير خرائط JSON إلى الواجهة.
- تقرأ Data DTO الوضع الفعلي مع التحقق من حقول البحث (`count`) والمعلومات العددية الموجودة.
- يتحقق Repository بعد الاستجابة من تطابق `entity.mode` مع وضع الطلب (بحث عند وجود `q` غير فارغ، أو تصفح عند عدم وجوده)، مع استمرار تحقق `entity.page` وتثبيت بصمة العقد والجلسة.
- عند عدم التطابق يتحول الخطأ إلى `TypedReadFailureKind.invalidResponse`، وتظهر حالة خطأ قابلة لإعادة محاولة الصفحة، بدل وضع نتائج ليست من البحث المطلوب داخل القائمة.
- العقود القديمة التي لا تدعم `search` المُرقّم تظل محصورة في `page`، ويمنع المستودع قبول أي وضع آخر.
- اختبارات DTO وWidget **المولّدة** أصبحت تعرف النوع الجديد؛ اختبار DTO المولّد يختبر نجاح وضع `search` وفشل `count` غير المطابق.

## الإثبات والحدود

اجتازت 15 مجموعة اختبار مصدرية معزولة لمسارات W5 السابقة بعد التعديل، وتم فحص نصوص Dart المولّدة. لا يعتبر هذا بديلاً عن تشغيل `dart analyze` أو `flutter test` على مشروع مولّد، أو قاعدة بيانات وBackend حيّة أو جهاز حقيقي. تظل W5–W8 والاعتمادية الإنتاجية بحاجة إلى تحقق فعلي، وقرار الإنتاج `NO_GO`.
