# RC281 — W5 Signed datetime range filters with calendar UI

**Reference source:** Flutter main `95518eaf9f7c5aa11160cc52ac16d19e611fcd3d` (merged RC280), Backend main `b61e7d6bb69f4d330a16dc045bc7428a07f8be46` (RC279).

## Delivered
- Generate `From/To` date bounds **only as a complete pair**, and only for a nonsensitive `datetime` item field independently verified against the signed Fable operation and OpenAPI `format: date-time`. Do not invent unknown or partially declared bounds.
- Real read-only Flutter calendar controls; `From` selects UTC start of day, `To` selects UTC end of day, with clear actions. The picker is currently restricted to 1900–2100 as a UI choice, not a Backend limit.
- Gate asynchronous selection on a pinned identity epoch; stale account pickers cannot publish filters. Clearing or changing date resets Infinite Scroll to page one.
- The gateway only accepts canonical UTC ISO 8601 (as generated by the calendar): `DateTime.tryParse` plus a canonical round trip rejects normalized impossible dates; reversed From/To is rejected before HTTP. Blank bounds are omitted. No date equality is sent concurrently.
- Preserve RC278 equality controls, RC280 numeric ranges, RC274 global paginated search, and existing signed session/identity logic.

## Evidence
- **8/8 isolated JavaScript test callbacks executed** directly against the actual current source planner and renderer, including three prior RC278 and three RC280 source regressions and two RC281 date cases.
- The tests live in `test/rc278-signed-equality-filters.test.mjs` and are runnable by Node in a full checkout. This isolated verification is **not** full repository `node --test`, Dart/Flutter SDK, compiled Android/iOS, or live Nest+MySQL.
- Backend signed permission and recordAccess rules remain authoritative. Real project E2E and production readiness remain **NO_GO**.
